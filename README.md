# Клинический компас

Цифровой помощник врача-терапевта для ведения пациентов с тревожной и депрессивной симптоматикой. Пациент в приложении ведёт дневник самочувствия, отмечает приём препарата, заполняет GAD-7 и PHQ-9, раз в неделю — короткую PHQ-4, сообщает о побочных эффектах и пишет врачу. Система проверяет каждую запись по правилам из базы знаний: при риске врач в ту же секунду получает алерт с источником, а пациент видит экран экстренной помощи. При назначении Авиандра врач видит пункты инструкции, которые нужно учесть. Решения принимает только врач: система предлагает, врач принимает или отклоняет.

Кейс-чемпионат «Клинический компас» (Авинейро / ГК ХимРар, НМИЦ им. Сербского, Сеченовский Университет). Демо-препарат — Авиандр (маритупирдин).

## Ключевые функции

### Пациент

| Функция | Как работает |
|---|---|
| Дневник | Тревога, настроение и сон по шкале 0–10 и заметка — раз в день |
| Приём препарата | «Принял сегодня» или «Пропустил» по каждому назначению врача |
| Опросники GAD-7 и PHQ-9 | Раз в 14 дней; раньше срока — кнопка «Стало хуже — пройти сейчас» |
| Короткий опросник PHQ-4 | Раз в неделю: 2 вопроса о тревоге и 2 о депрессии; каждый день — дневник самочувствия |
| Побочный эффект | Описание своими словами, тяжесть и отметка «понадобилась медицинская помощь» — это серьёзное нежелательное явление |
| Чат с врачом | Сообщения врачу и ответы врача |
| Напоминания | 3 дня без записей — синее напоминание заполнить дневник; любая новая запись его снимает. Приём меньше 80 % дней за неделю — напоминание написать врачу |
| Кнопка «Нужна срочная помощь» | Экран с номерами 112 и 103 открывается сразу, до любых вопросов. Если пациент напишет, что случилось, причина уходит врачу сообщением в чат и критичным алертом |
| Экран помощи при риске | Пункт 9 PHQ-9 ≥ 1 или слова о смерти и самоповреждении в тексте — экран 112 и 103; если алерт ушёл врачу, пациент видит «Ваш врач уже получил уведомление» |
| Регистрация | По коду от врача и с согласием на обработку персональных данных |

### Врач

| Функция | Как работает |
|---|---|
| Список пациентов | Диагнозы (коды МКБ-10), риск, открытые алерты и последние баллы шкал |
| Алерты в реальном времени | Уведомление всплывает сразу (WebSocket). В алерте — время создания и доставки, данные, на которых сработало правило, и источники. Кнопка «Принято к сведению» |
| История алертов | Все алерты пациента, включая принятые к сведению; каждый открывается целиком |
| 5 дней без записей | Алерт «свяжитесь с пациентом». Такие правила проверяются ещё и по расписанию, раз в час: у молчащего пациента нет записей, которые запустили бы проверку |
| Предложения врачу | Направление к психиатру «ОБЯЗАТЕЛЬНО» или «ЖЕЛАТЕЛЬНО». Врач нажимает «Принять» или «Отклонить»; принятое направление оформляется, решение пишется в журнал аудита. К одному специалисту открыто не больше одного предложения, даже если сработало несколько правил; «обязательно» заменяет открытое «желательно». Когда пациент направлен, остальные предложения к этому специалисту закрываются с пометкой «закрыто: уже направлен» |
| Направление по решению врача | Врач сам направляет к психиатру, психотерапевту или неврологу: уровень «ОБЯЗАТЕЛЬНО» или «ЖЕЛАТЕЛЬНО», причина обязательна. Все направления — в разделе «Направления» карточки с пометкой, откуда они: по предложению правила или решение врача |
| Проверка назначения Авиандра | Пункты из листка-вкладыша в ГРЛС: противопоказания, «с осторожностью», взаимодействия. Система сверяет их с диагнозами МКБ-10, возрастом, полом и текущими назначениями; чего карточка не знает, врач проверяет у пациента. Врач отмечает каждый пункт; при противопоказании из карточки назначить можно только с обоснованием. Система ничего не запрещает, всё пишется в аудит. Доза в форме — по инструкции, 20 мг 2 раза в сутки; врач может изменить |
| Триаж свободного текста | Сообщения пациента, причины срочной помощи и описания побочных эффектов ML-сервис размечает уровнем риска. Текст о смерти или самоповреждении — критичный алерт и предложение «обязательно» к психиатру. Сейчас триаж — словарь шаблонов, работает без LLM |
| Карточка пациента | Шкалы, дневник, терапия и приверженность, нежелательные явления, чат |
| Отмена назначения | Кнопка «Отменить назначение» с подтверждением и необязательной причиной; причина пишется в аудит |
| Приглашение пациента | Код и ссылка для регистрации: код подставляется сам; подсказка, что делать дальше |
| Извлечение из истории болезни | LLM извлекает диагнозы, сопутствующие болезни, препараты, аллергии, баллы шкал и флаги риска с цитатой из текста. Пока доступно через API ML-сервиса (`POST /extract`), в карточку врача не встроено |

## Принципы

- **Решает врач.** Система только предлагает: предложение проходит путь `proposed → accepted / rejected` (или `superseded` — закрыто без действия, когда пациент уже направлен), и только решение врача делает его клиническим действием. Назначает тоже только врач. Решения, назначения и подтверждения алертов пишутся в журнал аудита.
- **У каждой подсказки источник.** Алерт, предложение и пункт инструкции ссылаются на запись из `kb/sources.yaml`: статью с DOI, клиническую рекомендацию Минздрава, инструкцию из ГРЛС или зафиксированное решение команды.
- **Правила — ядро, ИИ — только извлечение и разметка.** Алерт создаёт правило из `kb/rules`. LLM извлекает факты из истории болезни, триаж только размечает текст уровнем риска, а что делать с разметкой, решает правило. Без ML-сервиса правила по шкалам, приёму и нежелательным явлениям работают как обычно.
- **Клиническая логика — в `kb/*.yaml`.** Шкалы, правила, препараты и источники меняются без правки кода; бэкенд проверяет схему базы знаний при старте ([kb/README.md](kb/README.md)).

## Быстрый старт (всё в Docker)

Нужны [Git](https://git-scm.com/downloads) и [Docker Desktop](https://www.docker.com/products/docker-desktop/), запущенный перед командами.

```bash
git clone https://github.com/ladnlav/psycho-assistant.git
cd psycho-assistant
cp .env.example .env
docker compose up -d --build                         # первый раз — несколько минут
docker compose exec backend python -m app.seed       # демо-врач и демо-пациент с данными за 4 недели
docker compose exec backend python -m app.scenarios  # 5 пациентов демо-сценариев
```

- Приложение: http://localhost:8080
- API и Swagger: http://localhost:8000/docs
- ML-сервис: http://localhost:8001/docs

Демо-аккаунты: `doctor@example.com` и `patient@example.com`, пациенты сценариев — `scenario1@example.com` … `scenario6@example.com`. Пароль у всех — значение `SEED_PASSWORD` из `.env`.

Остановить: `docker compose down` (данные сохранятся). После перезапуска Docker или компьютера стенд поднимается сам. Стирают введённые данные только `docker compose down -v` (вся база) и `app.scenarios … --reset` (пациенты сценария).

## Как показать демо

Врача и пациента лучше открыть в **двух разных браузерах** (или в обычном окне и в режиме инкогнито): в одном окне браузера одновременно можно быть только одним пользователем.

1. **Врач** входит как `doctor@example.com` — видит список пациентов с последними баллами шкал. Карточку пациента не закрываем.
2. **Пациент** входит как `patient@example.com` — главная страница: самочувствие, отметка о приёме Авиандра, опросники, сообщение о побочном эффекте, чат с врачом. История демо-пациента заканчивается вчера, поэтому сегодня можно показать, как он отмечает самочувствие и заполняет GAD-7, которую уже пора пройти.
3. Пациент открывает **PHQ-9** и в пункте 9 отмечает «В течение нескольких дней» → сразу видит экран помощи с телефонами 112 и 103.
4. У **врача** в ту же секунду всплывает уведомление «Критично», в карточке пациента — красный алерт с временем доставки и источниками, ниже — предложение «ОБЯЗАТЕЛЬНО» направить к психиатру.
5. Врач нажимает **«Принять»** → предложение помечается «принято врачом», направление оформлено, всё записано в журнал аудита.
6. Пациент нажимает **«Нужна срочная помощь»** → экран 112 и 103 сразу; пишет, что случилось → у врача критичный алерт и сообщение в чате.
7. Дополнительно: история алертов, дневник и графики в карточке, «Пригласить пациента», чат, пациенты сценариев 1–5.

Повторный алерт по тому же правилу появляется только на новые данные — например, если пациент снова отметит пункт 9 в PHQ-9. Дневник, отметки о приёме и другие шкалы его не вызывают. Чтобы начать демо с чистого листа: `docker compose down -v`, затем снова `up -d --build`, `app.seed` и `app.scenarios`.

## Архитектура

```
Браузер (PWA) ─► frontend :8080 ─ /api, /ws ─► backend :8000 ─► db :5433 (PostgreSQL)
                                                  │    └─ kb/*.yaml, scenarios/*.yaml (только чтение)
                                                  └─► ml :8001 ─► LLM (OpenAI-совместимый API)
backup ─ pg_dump раз в 2 часа ─► ./backups
```

| Сервис | Что делает | Порт на хосте |
|---|---|---|
| `frontend` | React 19 + Mantine 9, PWA; nginx отдаёт сборку и проксирует `/api` и `/ws` на backend | 8080 |
| `backend` | FastAPI + SQLAlchemy: роли, связь врач–пациент, шкалы, дневник, приём, нежелательные явления, движок правил, алерты по WebSocket, решения врача, аудит | 8000 |
| `ml` | FastAPI: `POST /extract` — извлечение через LLM, `POST /triage` — разметка текста | 8001 |
| `db` | PostgreSQL 16 | 5433 |
| `backup` | Резервная копия базы раз в 2 часа, хранит последние 24 | — |
| `ollama` | Необязательно, профиль `llm`: локальная LLM в контейнере, нужна NVIDIA GPU | 11434 |

LLM подключается по адресу из `.env`: основной вариант — модель на V100 через JupyterHub, запасной — Ollama на своём компьютере или SSH-туннель к серверу (раздел [«LLM»](#llm)).

### Лицензии шкал

GAD-7, PHQ-9 и PHQ-4 — свободные: правообладатель (Pfizer) не требует разрешения на воспроизведение, перевод и показ. HADS, BDI-II, STAI, ISI и MMAS-8 сознательно не используются: для них нужно письменное разрешение правообладателя. Загрузчик базы знаний не примет шкалу с `license.type: licensed` без `permission_obtained: true`.

## Данные и 152-ФЗ

- В репозитории и на демо — только вымышленные пациенты: демо-аккаунты, 5 сценариев, истории болезни для оценки извлечения.
- Пациент регистрируется только с согласием на обработку персональных данных (152-ФЗ). Реальные данные пациентов не должны уходить во внешние сервисы.
- Модель работает на выделенном сервере — V100 в университетском JupyterHub, доступ по токену, — а не во внешнем облачном API. ML-сервис работает с любым OpenAI-совместимым сервером, поэтому модель можно поставить и на сервер клиники.
- Журнал аудита хранит регистрацию, записи шкал, нежелательные явления, просьбы о помощи, алерты, просмотры карточки, назначения и решения врача.

```bash

# бэкенд — http://localhost:8000
cd backend
```

## Резервные копии

Сервис `backup` в docker compose раз в 2 часа снимает копию базы в папку `backups/` (в git не попадает) и хранит последние 24 — двое суток. RPO — 2 часа: при сбое теряем данные не больше чем за 2 часа. Интервал и число копий задаются в `.env` переменными `BACKUP_INTERVAL_S` и `BACKUP_KEEP`. Время в имени файла — UTC; ход работы — `docker compose logs backup`. Копии лежат на том же компьютере, что и база, и переживают `docker compose down -v`, но не потерю диска; в реальной эксплуатации их нужно уносить на отдельное хранилище.

Восстановление в отдельную базу, рабочую не трогаем:

```bash
docker compose cp backups/<файл>.dump db:/tmp/restore.dump
docker compose exec db createdb -U compass compass_restore
docker compose exec db pg_restore -U compass -d compass_restore /tmp/restore.dump
docker compose exec db psql -U compass -d compass_restore -c "select count(*) from alerts"
```

Время от начала восстановления до успешной проверки — RTO. Если `compass_restore` уже есть, сначала `docker compose exec db dropdb -U compass compass_restore`.

## LLM

ml-сервис обращается к любому OpenAI-совместимому серверу (`LLM_BASE_URL`, `LLM_MODEL` в `.env`). По умолчанию это Ollama на `localhost:11434`. В репозитории и в разработке — только вымышленные данные; реальные данные пациентов не должны уходить во внешние сервисы (152-ФЗ).

Какая модель куда помещается (сжатие до 4 бит, оценка с запасом ~1 ГБ на контекст):

| Модель | Память | GPU 4 ГБ | V100 16 ГБ | V100 32 ГБ |
|---|---|---|---|---|
| `qwen2.5:3b` | ~3 ГБ | ✓ (качество ниже) | ✓ | ✓ |
| `qwen2.5:7b` — по умолчанию | ~6 ГБ | ✕ | ✓ | ✓ |
| `qwen2.5:14b` | ~10 ГБ | ✕ | ✓ | ✓ |
| `qwen2.5:32b` | ~21 ГБ | ✕ | ✕ | ✓ |

### Модель на V100 через JupyterHub — основной вариант

Модель работает в GPU-сессии университетского JupyterHub: там запущены Ollama с `qwen2.5:14b` и небольшой прокси на порту 11435. JupyterHub отдаёт этот порт по https и пускает только с токеном. Для приложения это обычный OpenAI-совместимый сервер, SSH не нужен.

**1. Строки в `.env`.** Адрес и токен даёт Матвей. Токен храним только в `.env`: не коммитим и не пересылаем в общие чаты.

```ini
LLM_BASE_URL=https://<адрес-JupyterHub>/user/<логин>/proxy/11435/v1
LLM_BASE_URL_DOCKER=https://<адрес-JupyterHub>/user/<логин>/proxy/11435/v1   # тот же адрес — для контейнера ml
LLM_API_KEY=<токен JupyterHub>
LLM_MODEL=qwen2.5:14b
```

**2. Один раз: окружение для скриптов запуска**

```bash
cd ml/server/qwen_remote_v2
py -3.12 -m venv .venv                            # Ubuntu: python3 -m venv .venv
.venv/Scripts/pip install -r requirements.txt     # Ubuntu: .venv/bin/pip install -r requirements.txt
```

**3. Запустить и остановить модель** — в Git Bash на Windows или в терминале Ubuntu, из `ml/server/qwen_remote_v2`:

```bash
./start_llm.sh                # поднимает GPU-сессию, если её нет, и запускает Ollama с прокси
./stop_llm.sh                 # останавливает Ollama; GPU-сессия остаётся
./stop_llm.sh --session       # заодно освобождает GPU-сессию
```

Запуск с нуля занимает около 2 минут. Повторный `./start_llm.sh` ничего не ломает: если модель уже отвечает, он только сообщит `Ollama and OpenAI-compatible proxy already available`.

**4. Проверить**

```bash
curl -H "Authorization: Bearer <токен>" https://<адрес-JupyterHub>/user/<логин>/proxy/11435/v1/models
```

Ответ — JSON со списком моделей; адрес без `/models` отвечает 404, это нормально. Затем `docker compose up -d ml` пересоздаст контейнер с новыми переменными, и `POST /extract` на http://localhost:8001/docs пойдёт в модель на V100: короткая история болезни обрабатывается примерно за 10–15 секунд. `python -m eval.run_eval` в `ml/` берёт адрес из того же `.env`.

**Что важно знать**

- GPU-сессия живёт до 4 часов, потом JupyterHub её останавливает, и `/extract` отвечает «503: LLM недоступна». Тогда снова `./start_llm.sh`. Перед демо запускаем модель заранее и проверяем `/models`.
- `ERROR: LLM_BASE_URL в .env должен быть адресом прокси JupyterHub` — в `.env` остался адрес локальной Ollama.
- Ответ 302 с переходом на `/hub/login` или 403 — токен не передан, отозван или у него нет прав на GPU-сессии.
- Серверная часть — Ollama с `qwen2.5:14b`, `~/start_qwen.sh`, `~/stop_qwen.sh` и `~/ollama_proxy.py` в домашней папке на кластере. Копии этих скриптов лежат в `ml/server/qwen_remote_v2/` с префиксом `from_server_` ([README](ml/server/qwen_remote_v2/README.md)).

### Запасной вариант: Ollama на сервере и SSH-туннель

Если JupyterHub недоступен, Ollama можно запустить на сервере с V100 и пробросить до своего компьютера SSH-туннелем. Для приложения модель тогда выглядит как `localhost:11434`, и ничего перенастраивать не нужно.

На V100 используем Ollama, а не vLLM: у этой видеокарты нет поддержки bf16, а свежие версии vLLM могут её не поддерживать.

**1. На сервере: проверить карту и поставить Ollama без root**

```bash
nvidia-smi                                   # объём памяти (16 или 32 ГБ) и версия CUDA

mkdir -p ~/ollama && cd ~/ollama
curl -L https://ollama.com/download/ollama-linux-amd64.tgz -o ollama.tgz
tar -xzf ollama.tgz                          # появятся ~/ollama/bin и ~/ollama/lib
```

Если по ссылке скачается архив `.tar.zst`, распаковать его так: `tar --zstd -xf <файл>`. Все сборки лежат на github.com/ollama/ollama/releases.

```bash
# добавить в ~/.bashrc, чтобы работало и после переподключения
export PATH="$HOME/ollama/bin:$PATH"
export OLLAMA_MODELS="$HOME/ollama/models"   # куда класть модели; нужно 5–20 ГБ диска
```

**2. На сервере: запустить и проверить**

```bash
tmux new -s llm                              # сессия переживёт отключение SSH
ollama serve                                 # слушает 127.0.0.1:11434
# Ctrl+B, затем D — отсоединиться; вернуться: tmux attach -t llm

ollama pull qwen2.5:7b                       # ~4,7 ГБ; потом можно сравнить с qwen2.5:14b
ollama run qwen2.5:7b "Ответь одним словом: готово"
ollama ps                                    # в столбце PROCESSOR должно быть 100% GPU
```

**3. На сервере: оценка точности извлечения** (туннель для этого не нужен)

```bash
git clone https://github.com/ladnlav/psycho-assistant.git
cd psycho-assistant/ml
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest -q                # 7 passed
LLM_BASE_URL=http://localhost:11434/v1 LLM_MODEL=qwen2.5:7b .venv/bin/python -m eval.run_eval
```

Отчёт с точностью и полнотой по полям сохранится в `ml/eval/runs/<время>/report.json`.

**4. На своём компьютере: SSH-туннель к модели**

```bash
ssh -N -L 11434:localhost:11434 <логин>@<адрес-сервера>
```

Окно с туннелем держим открытым, пока нужна модель. Команда `ssh` есть в Git Bash и в PowerShell на Windows 10/11. Проверить туннель можно из другого окна:

```bash
curl http://localhost:11434/api/tags         # в PowerShell: curl.exe ...
```

Ответ — JSON со списком моделей. После этого приложение (`docker compose up -d`) и `python -m eval.run_eval` на своём компьютере работают с моделью на V100. В `.env` должно стоять `LLM_MODEL=qwen2.5:7b` или та модель, что скачана на сервере.

Проверить извлечение через приложение: откройте http://localhost:8001/docs → `POST /extract` → **Try it out**, вставьте текст истории болезни → **Execute**. Первый ответ может занять 20–60 секунд, пока модель загружается в память.

**Если GPU на кластере выдаётся через очередь задач (SLURM)**

Сервер модели тогда работает на вычислительном узле, а не на узле входа. Команды зависят от правил кластера — уточните их у администраторов.

```bash
srun --gres=gpu:1 --time=08:00:00 --pty bash    # получить узел с GPU на 8 часов
hostname                                        # имя узла, например gpu07
OLLAMA_HOST=0.0.0.0:11434 ollama serve          # слушать сеть кластера, а не только localhost
```

Туннель на своём компьютере тогда идёт через узел входа:

```bash
ssh -N -L 11434:gpu07:11434 <логин>@<узел-входа>
```

Учтите: когда закончится время задачи (`--time`), сервер модели остановится. Для демо на предзащите и финале заранее сохраним результаты извлечения и запишем видео — на случай, если туннель или кластер подведут.

**Частые проблемы**

- `bind: address already in use` — порт 11434 занят. На своём компьютере это обычно локальная Ollama: остановите её или пробросьте туннель на другой порт (`-L 11435:localhost:11434`) и поставьте в `.env` `LLM_BASE_URL_DOCKER=http://host.docker.internal:11435/v1`.
- `ollama ps` показывает CPU вместо GPU — проверьте `nvidia-smi`: видна ли карта и не занята ли она чужой задачей.
- `/extract` отвечает «503: LLM недоступна» — не запущен туннель или `ollama serve`; проверьте `curl http://localhost:11434/api/tags`.
